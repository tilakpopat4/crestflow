# Threat-Model Checklist & Security Invariants Verification (Revised)

This document cross-references each of the **15 Non-Negotiable Security Requirements** and additional DoS protections against its exact implementation safeguard, defense mechanism, and automated test location.

---

| # | Security Requirement | Attack Vector / Risk | Architectural Defense & Mitigation | Test Location |
| :- | :--- | :--- | :--- | :--- |
| **1** | **Never trust client-side redirects** (`/order-success` etc.) | Malicious user navigates directly to success URL or intercepts browser response to activate Pro. | Client redirect does NOT activate any subscription. Only a server-side verified provider event/status call can update `subscriptions.status = 'active'`. | `tests/integration/webhook.test.ts` (test: `rejects client-spoofed activation`) |
| **2** | **Verify webhook authenticity** | Attacker sends fake POST to `/api/youpi-webhook` mimicking gateway success. | HMAC-SHA256 signature calculated over raw unparsed request bytes with `YOUPI_WEBHOOK_SECRET`. Constant-time comparison (`crypto.timingSafeEqual`). Replay protection window rejects timestamps > 5 minutes old. | `tests/integration/webhook.test.ts` (test: `forged signature rejected 401`, test: `stale timestamp rejected 400`) |
| **3** | **Idempotency** | Gateway retries webhook or observer fires multiple times, erroneously extending subscription twice. | PostgreSQL unique constraint on `payments.provider_order_id` + transactional check in confirmation service. If already `SUCCESS`, logs retry and returns HTTP 200 without second period addition. | `tests/integration/webhook.test.ts` (test: `duplicate webhook idempotency`) |
| **4** | **Amount & Plan Validation** | User alters checkout payload to pay ₹1 instead of ₹49 for Pro. | Server decides price strictly from `plans` table. On webhook confirmation, server verifies `amountPaise == plan.price_paise`. Mismatch flags payment as `SUSPICIOUS`, logs alert, and never activates access. | `tests/integration/webhook.test.ts` (test: `underpaid amount marked suspicious`) |
| **5** | **Suspicious / Failed / Expired states never grant access** | Ambiguous or rejected payment grants features. | State machine explicitly enforces that only final `SUCCESS` status can transition a subscription to `active`. `SUSPICIOUS` status routes directly to Admin Review Queue. | `tests/unit/entitlements.test.ts` (test: `suspicious state denies entitlements`) |
| **6** | **Atomic Period Extension Math** | Race condition when extending an active subscription results in overwritten expiration dates. | Executed inside a single PostgreSQL transaction: `current_period_end = GREATEST(now(), COALESCE(current_period_end, now())) + (plan.period_days \|\| ' days')::INTERVAL`. | `tests/unit/periodMath.test.ts` (test: `atomic extension calculation`) |
| **7** | **Zero Secret Leaks in Code or Logs** | `YOUPI_WEBHOOK_SECRET` or `SUPABASE_SERVICE_ROLE_KEY` committed, logged, or exposed in Vite bundle. | `SUPABASE_SERVICE_ROLE_KEY` is loaded ONLY on Express server, NEVER prefixed with `VITE_`. Vite bundle is tested to ensure zero service-role keys exist in client assets. Masked formatters prevent logging. | `tests/unit/securityAudit.test.ts` (test: `no secrets in Vite bundle or logs`) |
| **8** | **Server Decides Price and Plan** | Client-side API tampering passes custom `amount` parameter in POST request. | Backend endpoint `/api/billing/create-order` only accepts `planCode`. Server queries PostgreSQL `plans` table for the authoritative price in paise. Client `amount` parameter is completely ignored. | `tests/integration/billingApi.test.ts` (test: `server ignores client amount`) |
| **9** | **Authorization & Rate Limiting** | Malicious script spams order creation or webhook endpoint, exhausting gateway resources. | Express rate limiter (`express-rate-limit`): max 3 order creations per user/IP per 10 minutes. Webhook endpoint rate limited to 60 requests/minute. Users can only view their own orders via Supabase JWT. | `tests/integration/abuseControls.test.ts` (test: `order creation rate limit exceeded`) |
| **10** | **PII & Financial Data Masking** | Plaintext phone numbers, OTPs, or full bank account/VPA data dumped into application logs. | Logging utility runs regex masking on phone numbers (`XXXXXX1234`), VPA addresses (`u***@upi`), and bank UTRs (`********1234`). OTPs are never logged. | `tests/unit/securityAudit.test.ts` (test: `pii masking sanitizer`) |
| **11** | **Data Preservation on Downgrade/Expiry** | Lapsed subscription deletes past user data, client records, or invoices. | Schema and application guardrails ensure expiry ONLY restricts creating *new* items or issuing new invoices. Past invoices, client contact info, and work logs are strictly read-only and always downloadable. | `tests/unit/entitlements.test.ts` (test: `expired user retains read and export access`) |
| **12** | **Append-Only Audit Log** | Admin or automated service changes subscription status without record. | Every transition (`previous_status -> new_status`) writes an immutable row to `public.subscription_audit_logs` recording timestamp, actor, reason, and metadata. | `tests/integration/webhook.test.ts` (test: `audit log created on status change`) |
| **13** | **Feature Flag Guard (`BILLING_ENABLED`)** | Unfinished billing changes break existing platform workflow. | Backend and frontend wrap all billing checks behind `BILLING_ENABLED` environment variable (default: `false`). When `false`, the tool operates exactly as before without paywall enforcement. | `tests/integration/featureFlag.test.ts` (test: `billing disabled maintains legacy mode`) |
| **14** | **PaymentProvider Abstraction** | Business logic tightly coupled to YouPI PG internals. | Clean TypeScript interface `PaymentProvider` (`createOrder`, `verifyWebhook`, `queryStatus`, `cancelOrder`). Swapping to Razorpay or Stripe only requires implementing a new adapter class. | `tests/unit/providerAdapter.test.ts` (test: `mock provider implements interface`) |
| **15** | **Reconciliation & Safe Manual Override** | Gateway webhook drops due to temporary network failure, leaving customer unverified. | Scheduled cron job queries gateway for pending orders older than 15 minutes. Admin console provides safe manual "Mark Paid" and "Reject" buttons with mandatory reason prompt and audit logging. | `tests/integration/reconciliation.test.ts` (test: `reconciliation recovers pending payment`) |
| **16** | **Client-Side RLS Tampering Prevention** | User tries to run `supabase.from('subscriptions').update({ status: 'active' })` directly from browser console. | PostgreSQL RLS has NO insert/update/delete policies for `anon` or `authenticated` roles on billing tables. All writes require `service_role`. Attempt returns Postgres error `42501` (`insufficient_privilege`). | `tests/integration/rlsBypass.test.ts` (test: `client write attempt fails with 42501`) |
| **17** | **Single-Slot FIFO Queue DoS Target** | Attacker spins up hundreds of sessions to starve other buyers from the YouPI gateway slot. | Three-tier protection: 1) Verified email required (`email_verified = true`); 2) Max 1 concurrent open order per user; 3) 5-minute aggressive session expiry with automatic slot cancellation via `/api/v1/checkout/{id}/cancel`. | `tests/integration/abuseControls.test.ts` (test: `single slot queue dos blocked`) |
| **18** | **Server-Side Paywall Enforcement** | Attacker calls direct Supabase client queries or backend API to create clients/invoices while unsubscribed. | Enforced at PostgreSQL layer: `WITH CHECK (auth.uid() = user_id AND public.has_active_access(auth.uid()))`. Enforced at Express layer: `requireActiveSubscription` middleware. | `tests/integration/rlsBypass.test.ts` (test: `unsubscribed client write rejected by RLS`) |
